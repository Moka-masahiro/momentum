# モメンタム（自分用・日本株）

株AIアプリ「KabuAI」のプロモ動画を参考に作った、スマホ向けのアプリ。
**PC の電源は要らない。** 平日の昼（前場の引け後）と夕方に GitHub Actions が全銘柄の日足を取り直して計算し、
暗号化したデータと画面を GitHub Pages に置く。スマホではそのページを開くだけで、
ホーム画面に追加すればアドレスバーの無いアプリとして開ける。

もとは Stock Advisor（`D:\AI作業場\stock-advisor`）のスマホ画面 `/m/` として作ったもので、
2026-09-27 に独立させた。計算の中身は同じで、Stock Advisor のサーバーや DB には依存しない。

```
平日 11:53・17:17（Google Apps Script のタイマーが GitHub Actions を起動）
  JPX の銘柄一覧（約3,700社）＋ yfinance の日足2年分 ＋ 日経平均
    → 指標・シグナル・検証を計算（pipeline/momentum）
    → 画面ごとのデータを gzip → AES-256-GCM で暗号化（web/public/data/*.bin）
    → 画面をビルドして GitHub Pages に公開
スマホ
  https://<ユーザー名>.github.io/<リポジトリ名>/ を開く → 合言葉で復号して表示
```

## 初回の準備（GitHub）

1. GitHub のアカウントを作る（無料。メールアドレスと2段階認証が必要）
2. 空の **Public** リポジトリを作る（例: `momentum`。README などは作らない）
   - 無料プランの GitHub Pages は公開リポジトリでしか使えない。公開されるのはコードだけで、
     株価のデータはリポジトリに入れない（Actions から Pages に直接置く）
3. このフォルダーを push する
4. リポジトリの Settings → Secrets and variables → Actions → New repository secret で
   **`MOMENTUM_PASSPHRASE`** に合言葉を入れる（12文字以上を推奨。他で使っているパスワードは使わない）
5. Settings → Pages → Build and deployment の Source を **GitHub Actions** にする
6. Actions → daily → Run workflow で1回目を手で動かす（約10分）
7. スマホで `https://<ユーザー名>.github.io/<リポジトリ名>/` を開き、合言葉を入れる。
   Chrome の「︙」→「アプリをインストール」でホーム画面に置く
8. 決まった時刻に起動する外部のタイマーを置く（下の「外部のタイマー（Google Apps Script）」）

## 毎日の動き

- 平日 17:17 JST に、外部のタイマー（Google Apps Script。下の「外部のタイマー」）が GitHub Actions の daily を
  起動する（`workflow_dispatch`。手動の実行と同じく数秒で始まる）。18:47 JST に予備の起動があり、
  予備は、その日の17時以降に作ったデータがもう公開済みなら何もせずに終わる
- **GitHub 自身の定時実行（`schedule`）は5〜7時間遅れて届くので、予備にしている。** 同じ時刻を
  `.github/workflows/daily.yml` の cron にも書いてあり、届いた分は届いた時刻でどの回の分かを決める
  （`pipeline/should_build.py`）。平日 11:30〜12:30 なら前場の回、17時以降なら大引け後の回として、
  その回のデータがまだ無いときだけ作る。それ以外の時刻（朝・取引時間中・夜中）に届いた分は何もしない
  （以前は、夜中の 01:07 に届いた分が前日のデータを作り直していた）
  - このリポジトリの実測: 2026-09-29 の3回は 18:05・23:50・翌 01:07 に届いた（届いた順に 11:53・17:17・18:47 の
    分とみると、6時間12〜33分遅れ）。9/30 は 18:00 の時点で1回も届いていない（手動の実行 11:39・17:41 で補った）。
    実行が作られた時刻と始まった時刻は秒まで同じで、GitHub が実行を作る段階で遅れている（実行の順番待ちではない）
  - コミュニティの報告に出ていた他の公開リポジトリ（平日の UTC 06:10 に実行）の実測: 8/17〜8/26 は10分〜1時間48分遅れ、
    8/27・8/28 は12〜13時間、9/1〜9/28 は4時間53分〜7時間34分遅れ（月曜ほど遅い）。8/31 と 9/29 は届かなかった
  - GitHub のコミュニティでも、2026-08-26 の Actions の障害（Actions のトリガーを処理する DB の書き込みが飽和）の
    あとから同じ報告が続いている。分をずらす・ファイル名を変える・無効にして有効に戻す・コミットし直す、はどれも
    効かず、外から `workflow_dispatch` を頼む方法だけが効いたとされる。GitHub の回答は無く、状態のページは「正常」のまま
  - 最初は 17:00 ちょうどにしていた。2026-09-28 の分は届かなかった（遅れて届く前の 21:17 に cron を書き換えた）
- **平日 11:53 JST にも起動する（前場の引け後）。** 同じ処理で、当日の日足は前場の値までの途中経過になる
  （画面の日付の横に「前場」と出て、17時過ぎの実行で大引けのデータに置き換わる）。Yahoo の値は20分ほど
  遅れるので 11:30 の引けから少し置き、後場の始まる12:30までに公開する
  - いつ時点のデータかは実行した時刻で決める（11:30〜12:30 は前場、取引時間中の手動実行は「取引中」、
    それ以外と祝日は大引け後）。前場のときに、前の取引日に売買のあった銘柄の半分以上に当日の値が
    付いていなければ、取得がおかしいとみて公開しない
  - 前場の出来高は1日の出来高の中央値48%（流動性のある200銘柄×18日の30分足で実測。日によって43〜55%）。
    そこで前場の実行では「前場だけで1日平均の1.5倍（ふだんのペースの約3倍）」を出来高急増の目安にし、
    11:30 より後の開示は前場の値動きの理由にしない（後場の材料として銘柄詳細に出す）
  - 当日のシグナルやモメンタム度も前場の値で計算するので、大引けで変わることがある。
    Yahoo へのアクセスは1日2回になり、クラウドからのアクセスを断られる（HTTP 429）見込みは少し上がる
- 回帰テスト → 取得 → 計算 → 暗号化 → 画面のビルド → 公開、の順
- **取れた銘柄が9割未満、または最新の日足が6日より古ければ失敗にして公開しない。**
  壊れたデータで上書きせず、前日のデータが残る。失敗すると GitHub からメールが届く
- 値動きの理由の材料（適時開示・空売り残高・日々公表銘柄・逆日歩・全銘柄の信用残）は、取れなくても失敗にしない。
  取れなかったものは画面の設定「データの状態」に「取得できず」と出る（取得は2分弱。うち信用残の PDF の読み取りが約40秒）
- 実行記録を `pipeline/last_run.json` にコミットする。公開リポジトリは60日間変化が無いと
  定時実行が自動で止められるので、その対策も兼ねている
- 手で動かすときは Actions → daily → Run workflow（「外部のタイマーからの自動実行」は外したまま。いつでも作り直す）

## 外部のタイマー（Google Apps Script）

GitHub の定時実行が遅れるので、決まった時刻に起動する役だけを Google Apps Script に持たせている
（無料。今ある Google アカウントで使え、Google のサーバーで動くので PC は要らない）。コードは `timer/timer.gs`。

- 5分ごとに動き、平日の 11:53・17:17・18:47 を過ぎたら、その回を1回だけ頼む（時刻から5分以内）。
  頼めなかったときは30分の間、5分ごとにやり直す。土日は頼まない（祝日は頼むが、GitHub 側で前の取引日の
  終値のデータを作り直すだけ）
- 作り直すかどうかは GitHub 側（`pipeline/should_build.py`）が決めるので、同じ回を2度頼んでも余計には作らない
- 頼むときに使うトークンは、このリポジトリの Actions の操作だけができるもの（コード・合言葉・データには届かない）

### 準備（1回だけ）

1. GitHub でトークンを作る: 右上のアイコン → Settings → Developer settings → Personal access tokens →
   Fine-grained tokens → Generate new token
   - Token name は `momentum-timer` など。Expiration は1年（期限なしも選べるが、漏れたときに備えて付ける）
   - Repository access: **Only select repositories** → `momentum`
   - Permissions: Repository permissions の **Actions** を **Read and write**（Metadata: Read-only は自動で付く）
   - Generate token を押し、表示されたトークンをコピーする（この画面でしか見られない）
2. https://script.google.com で「新しいプロジェクト」を作り、`コード.gs` の中身を `timer/timer.gs` の中身に
   置き換えて保存する（プロジェクト名は `momentum-timer` など）
3. 左の歯車（プロジェクトの設定）→ いちばん下の「スクリプト プロパティ」に、プロパティ `GITHUB_TOKEN`・
   値に 1 のトークンを入れて保存する
4. エディタに戻り、実行する関数に `setup` を選んで「実行」。初回は Google の承認画面が出る。自分で作った
   スクリプトなので「Google はこのアプリを確認していません」と出ることがあり、「詳細」→「（安全ではないページ）に移動」
   → 許可、と進む。求められるのは外部サービスへの接続と、自分がいないときの実行（トリガー）
5. `testDispatch` を選んで「実行」。GitHub の Actions に daily の実行（workflow_dispatch）が1件増えれば成功
   （GitHub 側は時刻を見て、作る必要が無ければ check だけで終わる）
6. 左の時計（トリガー）で tick のトリガーを開き、エラーの通知を「今すぐ」にする（既定は1日1回のまとめ）

### ふだんの手入れ・困ったとき

- トークンの期限が切れると頼めなくなり、Google から tick の失敗のメールが届く（HTTP 401）。1 と同じ手順で
  作り直し、スクリプト プロパティの値を書き換える。そのあいだも GitHub 自身の定時実行（遅れる）は動く
- 動いているかは、Actions の一覧に daily の実行（workflow_dispatch）が平日 11:53・17:17・18:47 ごろに並ぶかで分かる。
  Apps Script の「実行数」にも5分ごとの tick が並ぶ
- 止めたいときは Apps Script のトリガーを消す（または GitHub でトークンを削除する）
- GitHub の定時実行の遅れが直れば、このタイマーが無くても動く。両方あっても GitHub 側で重複は作らない

## 指標・シグナル・検証

計算の中身は Stock Advisor の README「スマホ画面『モメンタム』」の節と同じ。要点だけ書く。

- **モメンタム度（0〜100）**: 20・60・120日の騰落率を、その銘柄の普段の値動き（60日の日次σ）で割った
  z 値を合成したもの。ランク S ≥85 / A ≥70 / B ≥55 / C ≥40 / D <40
- 他に SR・POWER・買い集め・安定度・RSI、シグナル6種（買い集め・出来高急増・高値ブレイク・
  ランクS入り・押し目反発・トレンド崩れ）、月足・週足・日足の向きと節目の整理（ルールベース）
- シグナルの成績は「翌営業日の始値 → N営業日後の終値」を**同じ期間の市場平均との差**で測る

### 検証の結果（2026-09-27 時点、2024-12-20〜2026-08-25 の407営業日）

**6つの指標も6種類のシグナルも、その後のリターン（市場比）を統計的に有意には説明していない。**

| 指標 | IC 20日後（t値） | 前半（〜2025-09-24） | 後半 |
|---|---|---|---|
| モメンタム度 | +0.018（0.51） | −0.004 | +0.036 |
| 安定度 | +0.025（0.93） | +0.048 | +0.013 |

- モメンタム度は、期間の切り方で向きが変わる（1年分で測ったときは前半が正・後半が負だった）。
  直近60日の平均は −0.16 で、いまは強い銘柄ほどその後に市場平均に負けやすい局面
- 安定度だけは、どの期間で測っても「落ち着いている銘柄ほどやや良い」向きだった（有意ではない）
- ランク別の20日後の市場比: S −0.28% / A +0.19% / B −0.15% / C −0.36% / D −0.53%
- シグナルはどれも市場比がほぼ0か負、勝率（市場比）は41〜46%

**ランキングは「いま強い銘柄」の一覧で、「これから上がる銘柄」の予想ではない。**
アプリの検証画面は毎日計算し直すので、期間が延びれば数字は変わる。
結論の文面も固定では書かず、その日のデータから作っている（固定で書くと、データが変わったときに嘘になる）。

## 値動きの理由（ニュース・需給・地合い・材料不明）

その日に**目立って動いた**銘柄に、動いた理由の手がかりをラベルで付ける（2026-09-28 追加）。
ホームの「きょう目立って動いた銘柄」、一覧画面「値動きの理由」、ランキング・シグナル・ウォッチリストの
各行、銘柄詳細の「値動きの理由」（根拠の開示・数字・直近30日の開示）に出る。計算は `pipeline/momentum/reasons.py`。

目立った動き＝**業種の中央値との差が普段の3倍以上**（普段＝直近60日の業種との差のばらつき）、
または**出来高が直前20日平均の3倍以上**。流動性のある銘柄で1日に数件〜数十件になる。
判定は上から順に当てはめる。

| ラベル | 条件 |
|---|---|
| 地合い | 当日±3%以上動き、業種全体も同じ向きに±1.5%以上動いて、この銘柄だけの動きは目立たない |
| ニュース | 前に売買が成立した日の引け（15:30）から当日の引けまでに、会社の適時開示がある |
| 需給（開示） | 窓の中の開示が、増資・転換社債・売出し・自社株買い・大株主の異動など株の需給に関わるものだけ |
| 地合い（連れ高） | 開示は無いが、同じ業種で普段の2倍以上を同じ向きに動いた銘柄が「3銘柄以上かつ業種の1割以上」ある |
| 需給（手がかり） | 開示は無いが、出来高3倍以上なのに値動きは小さい（業種比が普段の2倍未満・騰落±2%未満。3月末・9月末の権利付き最終日なら「権利取りの売買」）／信用取引の規制・日々公表・日証金の制限の対象（最新日だけ）／機関の空売り残高が直近4日以内の報告で0.5ポイント以上、値動きと同じ向きに増減（最新日だけ）／信用残が重く値動きを強める向き: 下げた日に信用買い残が出来高の5日分以上かつ信用倍率2倍以上（買い長）、上げた日に信用売り残が出来高の1.5日分以上かつ信用倍率1.5倍以下（最新日だけ）／3月末・9月末の権利落ち日の下げ |
| 材料不明 | どれにも当たらない |

- 開示の表題は決まった言葉で分類する（決算・業績修正・報道への回答・TOB・受注・提携…／増資・自社株買い…／
  定例＝ガバナンス報告書・招集通知など、理由にしない）。引け（15:30）以降・休日の開示は次の取引日の材料にする
- 開示を取得できなかった日を含むときは判定しない（開示があったのに「材料不明」と出さないため）

### 実測（流動性のある銘柄・2026-08-04〜09-25 の35営業日）

| 業種との差（普段の何倍か） | 会社の開示があった割合 |
|---|---|
| 1倍未満（普通の日） | 4% |
| 3〜4倍 | 36% |
| 4〜6倍 | 61% |
| 6倍以上 | 76% |

- 大きく動いた銘柄でも2〜6割には開示が無い。9/25 は小林製薬 +17% が「当社に関する一部報道について」、
  清水建設 −6% が転換社債の発行、リベルタ +21%・原田工業 +18% は開示なし（材料不明）
- 「出来高急増・値動き小」は、9/18（出来高3倍以上の銘柄が流動性のある銘柄の4.4%。普段は2%前後）や
  9/24 に多く出た。9/24 は中部飼料・井村屋・プリマハム・第一興商など株主優待の人気銘柄が並んだ
  （権利付き最終日 9/28 の前。優待・配当の権利取りの売買とみられるが、確かめたわけではない）
- 出来高急増の銘柄が多い日は、ほとんどが決算の集中日だった（2025-10-30、2026-02-13 など）。
  「市場全体で出来高が多い日なら需給」というルールは、決算による急増まで需給にしてしまうので入れていない
- 最初の版では、リベルタ（9/25 +21%）が1週間前（9/18）の空売りの買い戻しの報告で「需給」になった。
  当日の理由としては弱いので、空売りの手がかりは直近4日以内の報告だけにした
- 信用残（2026-09-25 申込み分・流動性のある1,922銘柄）: 買い残÷20日平均出来高は中央値1.1日・上位1割5.7日、
  売り残÷出来高は中央値0.1日・上位1割1.5日、信用倍率1倍以下（売り長）は12%。手がかりの閾値は上位1割に合わせた
- 信用残の手がかりは、最初は信用倍率を見ていなかった。アツギ（9/28 +12%）は売り残が出来高の2.6日分でも
  買い残がその5.4倍ある買い長で、「踏み上げ」と呼ぶのは言い過ぎだったので、倍率の条件を足した
- 9/28（9月末の権利付き最終日）は、流動性のある銘柄の70銘柄が「出来高急増・値動き小」になった。
  この日に限り「権利取りの売買」と出す（配当・優待取りの売買とみられるが、確かめたわけではない）

### データの出どころ（どれも無料・登録不要）

| 材料 | 入手先 | 備考 |
|---|---|---|
| 適時開示 | やのしん TDnet WEB-API（個人運営の非公式API） | 期間をまとめて頼むと件数が多いとき空が返るので1日ずつ取る（多い日でも3,000件弱）。応答の形が日によって揺れる（各行が `Tdnet` で包まれない日がある）ので両方読む |
| 空売り残高 | JPX「空売りの残高に関する情報」（毎日・Excel） | その日に届いた報告だけが載るので、直近5日分を合わせる |
| 日々公表銘柄など | JPX「日々公表銘柄等信用取引残高」（毎日・Excel） | 2026-09-28 に表題と形式（.xls → .xlsx）が変わった。列の位置に頼らず ISIN の手前から読む |
| 逆日歩 | JPX「品貸料」（毎日・Excel） | 権利取りの時期は優待目当てのつなぎ売りでも付くので、判定に使わず表示だけ |
| 全銘柄の信用残 | JPX「銘柄別信用取引残高」（毎日16時・**PDF のみ**） | 2026-09-28 から毎日公表（それまでは週1回）。前の取引日の申込み分。下記の検算つきで読む |

- **JPX のページはファイル名で探す。** 2026-09-28 の形式変更でページ番号が振り直され（品貸料が `01.html` → `02.html`）、
  その日の逆日歩が取れなかった。信用取引残高等のページを順に見て、ファイル名（`Premium_Charges.xlsx`・
  `YYYYMMDD_mtdaily.xlsx`・`YYYYMMDD_mtall.pdf`）で探す
- **信用残の PDF は検算して読む。** 文字を取り出すと数字の途中に空白が入る（`2,100` → `2,1 00`、`24,900` → `2 4,900`）。
  つなぎ方をすべて試し、「売り残＝一般信用＋制度信用」「買い残＝一般信用＋制度信用」と前日比の同じ関係が
  すべて合うものだけを採る。1通りに決まらない銘柄は使わない（2026-09-25 分は銘柄の行 4,254 行がすべて1通りに
  決まった。読まないのは優先株・社債型種類株式の7行と合計の3行）。3,000行未満しか読めなければ形式変更とみなして使わない
- 最初は日本の ISIN（JP…）の行だけを読んでいて、外国企業の株（メディシノバ・ビート・ホールディングスなど3銘柄）を
  取りこぼした。ISIN の国は問わないようにした
- PDF の読み取りには `pypdf`（BSD ライセンス・純 Python）を使う。109ページで約40秒

使わなかったもの（2026-09-27 に確認）
- **TDnet（東証の公式）**: robots.txt で自動取得をすべて禁止（`Disallow: /`）。直接は取りに行かない
- **Google ニュースの RSS 検索**: robots.txt で禁止。報道を無料で自動取得してよい入手先は見つかっていない
- **NHK の経済ニュース RSS**: robots.txt で AI 関連の自動取得を断っていて、更新も8月で止まっていた
- **東京商工リサーチ（TSR）**: 自動取得は許可・私的使用は可だが、中身は業界・倒産の分析と非上場企業の倒産速報で、
  個別銘柄の値動きの理由にならない。社名での照合は誤る（「アンビション」が別会社の上場企業に一致した）
- **日証金の貸借取引残高（CSV）**: 私的利用なら使えるが、証金経由の分だけなので、信用買残の約7%・信用売残の約3割しか
  含まない（2026-09-18 申込み分の実測: 融資 2.44億株 ÷ 買残 34.98億株、貸株 1.47億株 ÷ 売残 4.82億株）

### 限界

- **ニュースは会社の適時開示だけ。** 新聞報道・アナリストの格付け・テーマ買いは拾えない。会社が
  「一部報道について」を出したときだけ、報道が理由だとわかる
- 需給の手がかりは状況証拠で、原因の証明ではない
- 空売り残高・規制・信用残は当日分のファイルしか無いので、シグナル画面の過去の日付では判定に使えない（材料不明が多めに出る）
- 信用残は前の取引日の申込み分（公表が翌営業日16時のため）。その日の値動きの前の状態として見る
- 権利付き最終日・権利落ち日の判定は3月末・9月末だけ（銘柄ごとの権利確定日は持っていない）
- 開示の取得は個人運営の無料APIに頼る。止まったら理由の表示が「取得できず」になるだけで、本体は動く
- 信用残の PDF は JPX が形式を変えると読めなくなる。そのときは「取得できず」になり、信用残の手がかりが出なくなるだけ

### 株価の段差の補正

毎回2年分を取り直すので、取得の合間の株式分割による段差（Stock Advisor で起きた）は無い。
それでも Yahoo のデータ自体に未調整の分割が残っていることがあり（しまむら 2026-02-18、光陽社 2026-03-02）、
スピンオフ（Hamee 2025-10-30）もあるので、値幅制限を手がかりに補正している（`pipeline/momentum/data.py`）。
ストップ高の比例配分が続いた翌日は値幅が4倍に拡大される、呼値の丸めがある、といった落とし穴も考慮済み。

## 暗号化（合言葉）

無料の GitHub Pages は誰でもアクセスできる。そのまま置くと、自分用のアプリが他人にも見え、
Yahoo Finance 由来の株価を誰でも見られる形で再配布することにもなる。そこで全データを暗号化して置く。

- 鍵 = PBKDF2-HMAC-SHA256(合言葉, salt, 600,000回)、中身 = gzip した JSON を AES-256-GCM で暗号化
- 復号はスマホのブラウザの中（Web Crypto）で行う。合言葉はどこにも送らない
- salt（`pipeline/crypto.json`）は秘密ではない。毎日同じものを使うので、スマホは鍵を一度作れば済む
- 公開されるもの: コード、`pipeline/last_run.json`（実行日時と銘柄数・開示の件数と材料ごとの取得の成否だけ）、
  ページの存在とデータの大きさ・更新時刻。**株価や指標・値動きの理由の中身は、合言葉を知らなければ読めない**
- 検索エンジンには載せない（`robots.txt` と `noindex`）
- 合言葉を変えるときは secret を書き換えて Run workflow。スマホは自動で入力画面に戻る
- 弱点: 合言葉が推測されやすいと意味が無い（総当たりは手元で何度でも試せる）。12文字以上の、
  他で使っていない文字列にすること

## ウォッチリスト

サーバーが無いので、**その端末のブラウザの中にだけ**保存する（外には送らない）。
PC とスマホでは別々のリストになる。設定画面から銘柄コードをまとめて貼り付けて登録できる。

## 率直なリスクと制約

- **Yahoo がクラウドからのアクセスを断ることがある**（HTTP 429）。取得は時間を置いて3回までやり直し、
  それでも9割に届かなければその日は公開しない。続くようなら方式を見直す（PC で取得して push する等）
- yfinance は非公式。仕様変更で突然取れなくなることがある
- JPX の銘柄一覧は置き場所や形式が変わる（2026-09 に `.xls` → `.xlsx` になり、古いURLは404になった）。
  一覧ページからその時点のリンクを探すようにしてある
- **決まった時刻の起動は Google Apps Script に頼っている。** GitHub 自身の定時実行は 2026-08-27 ごろから
  5〜7時間遅れ、届かない日もあるので予備にしかならない。タイマーが止まる（トークンの期限切れ・Google 側の障害や
  仕様変更）と、更新はその遅れた定時実行だけになる。データ日付は画面の右上に出るので、古ければ気づける
- タイマーのトークンは Google のスクリプトの設定に置いてある。漏れると、他人がこのリポジトリの Actions を
  起動する・止める・記録を消すことはできる（コード・合言葉・データには届かない）。起動を繰り返されると
  Yahoo に断られる（HTTP 429）おそれはある。気づいたら GitHub でトークンを削除する
- 価格はリアルタイムではない（前営業日までの日足）
- 検証は約2年分で、特定の相場局面に強く依存する。上場廃止銘柄が抜けている（生存者バイアス）

## 判断の記録

- **GitHub を選んだ理由**: PC なしで毎日計算を回すには、どこかのクラウドの計算資源が要る。
  無料で、アカウント以外の登録（クレジットカード等）が要らず、実行と公開が同じ場所で済む
- **毎回2年分を取り直す理由**: 差分だけ足すと分割の調整が取得時期ごとにずれる。取得時間は
  リクエストの回数で決まり、期間の長さではほとんど変わらない。2年分あれば検証期間を1年半取れる
- **データをリポジトリに入れない理由**: 毎日30MB近いデータをコミットすると、リポジトリが
  際限なく膨らむ。Pages には Actions から直接置ける
- **Stock Advisor の `/m/` は残してある**（家の Wi-Fi 内で使う版）。不要になったら消してよい
- **値動きの理由を「ニュースか需給か」の2択にしなかった理由**: 大きく動いた銘柄の2〜6割は開示が無く、
  需給のデータでも説明がつかないものが多い。開示が無いものを需給と呼ぶと、報道やテーマ買いで動いた銘柄まで
  需給に見えてしまう。分からないものは「材料不明」と正直に出し、業種ごと動いたものは「地合い」に分けた
- **決まった時刻の起動を Google Apps Script にした理由**: GitHub の定時実行の遅れは、設定の変え方では
  直らないと報告されている。外から `workflow_dispatch` を頼めば数秒で始まる（手動の実行は毎回すぐ始まっている）。
  外から頼む手段のうち、Google Apps Script は無料で、今ある Google アカウントで使え、新しい登録が要らない。
  使わなかったもの: cron-job.org（登録が要り、トークンを第三者に預ける）、Cloudflare Workers の Cron Triggers
  （登録が要り、設定が重い）、スマホの自動化（電源と電波に左右される）、GitHub の cron を5〜15分おきに並べて
  届いた時刻で判断する（遅れて届かない日もある時計に頼ることになり、Actions の一覧も1日96〜288件で埋まる）、
  Actions のジョブを待たせ続けて時計にする（実行環境を占有し続けるのは、GitHub の利用規約が禁じる
  「見合わない負荷」に当たりうる）
- **トークンは `workflow_dispatch` 用に Actions の権限だけにした**: `repository_dispatch` でも外から起動できるが、
  コードも書き換えられる Contents の書き込み権限が要る
